# PROVE stage — safe, sandboxed verification

Takes a `CandidateFinding` **plus** its `ValidationResult` and attempts a
controlled, sandboxed proof that untrusted input actually reaches the
dangerous sink — without attacking real systems.

```
CandidateFinding + ValidationResult
        | gate: ONLY verdict == "true_positive"
        v
ProofPlanner (deterministic plan + trusted harness template)
        | SandboxRunner (fresh temp workspace, timeout, output caps, cleanup)
        v
ProofResult
```

Proof statuses:

| Status | Meaning |
|---|---|
| `verified` | the controlled observation matches the expected proof |
| `not_verified` | the observation did not match (or no plan exists for the type) |
| `blocked` | reserved for restrictions that cannot be guaranteed |
| `error` | harness timed out, crashed, or could not run |

## Validation gate

`ProofService.prove` refuses anything but `true_positive`:

* missing validation result → `ProofGateError`
* validation belongs to a different finding → `ProofGateError`
* `false_positive` / `uncertain` → `ProofGateError` (API maps to 409)

The gate is enforced inside the service, so callers cannot bypass it by
hand-crafting a proof request.

## Proof planner

`ProofPlanner` inspects the vulnerability type and returns a structured
`ProofPlan` (objective, allowed actions, expected observation, approved
harness, planner-controlled input). It never executes anything, and it never
uses attacker payloads: **finding snippets are data** — they are never
interpolated into the harness, never executed, and never shape the proof.

The harness templates (`planner.py`) are the ONLY code the sandbox executes.
They are trusted, internally generated, and each one asserts it is running
inside the sandbox workspace before doing anything. The `SandboxRunner`
rejects any harness name outside `APPROVED_HARNESSES` and any script that
differs from the trusted template.

## Sandbox policy

`SandboxPolicy` (defaults are maximally restrictive):

| Field | Default |
|---|---|
| `network_enabled` | `false` — NEVER enabled |
| `allow_loopback` | `false` — set only by the SSRF plan |
| `allowed_paths` | empty; the runner adds the fresh temp workspace |
| `timeout_seconds` | `10` |
| `max_output_bytes` | 16 KiB (stdout and stderr truncated) |
| `max_processes` | `1` (exactly one harness subprocess) |
| `temporary_directory` | created per run, removed after |

`SandboxRunner.run` creates a fresh `sast_prove_*` workspace, writes the
approved harness there, executes it with `cwd=workspace`, enforces the hard
timeout (kills the child), truncates output, and removes the workspace in a
`finally` block.

## SQL injection proof

A local, **in-memory** SQLite fixture (`users` table with two rows) inside
the harness. The same benign marker (`1 OR 1=1`) is executed two ways:

* unsafe: `SELECT * FROM users WHERE id = {marker}` (string construction)
* safe: `SELECT * FROM users WHERE id = ?` with a parameter

Verified when the unsafe construction returns rows and the parameterized
construction returns none — proving the sink interpolates untrusted input
into SQL. Read-only SELECTs only; no external database, no destructive
operations.

## Command injection proof

The harness builds the same command pattern the sink uses (`echo <input>`)
with two planner-controlled values:

* control value (`sast_prove_control_value`, no metacharacters) — must NOT
  create the marker file;
* a harmless marker containing a shell separator that writes a known file
  (`prove_marker.txt`) **inside the sandbox workspace only**.

Verified when the marker run creates the file and the control run does not.
The marker is generated by the planner (platform-aware `&` / `;`), never by
the finding. If safe verification is impossible, the plan returns
`not_verified` — an unrestricted command is never executed.

## SSRF proof

The harness starts a `ThreadingHTTPServer` bound to `127.0.0.1` on an
OS-assigned **ephemeral port** (port 0), in-process, and makes exactly one
request to the harness-generated URL `http://127.0.0.1:{port}/prove`. The
destination is generated by the harness — never by the analyzed input —
and dies with the harness process, so isolation is guaranteed. Verified when
the endpoint answers `200` with body `proved`.

`network_enabled` stays `false`; only `allow_loopback` is set for this plan.
There is no DNS resolution, no external host, no metadata endpoint, ever.

## Why network is disabled by default

An SSRF/CMDi/SQLi proof that could touch real destinations would be an
attack, not a proof. All observations are produced by controlled local
fixtures (in-memory SQLite, marker files in the temp workspace, an
ephemeral loopback server). The proof engine never requests anything beyond
the sandbox.

## Why proof is not production exploitation

A `verified` result means: *in the controlled fixture, the vulnerable
construction pattern behaves as the finding describes*. It says nothing
about the target's runtime, data, or defenses. The proof never runs the
repository's code, never probes infrastructure, and produces no exploit
payloads — it is evidence for triage, not an exploit.

## API

```
POST /api/findings/{finding_id}/prove
GET  /api/findings/{finding_id}/proof
```

Errors: `404` = finding or validation missing; `409` = verdict is not
`true_positive`.

## Limitations

* **Soft sandbox**: on a plain host the isolation is the temp workspace +
  policy + trusted harnesses (no OS firewall/seccomp/container jail). The
  harnesses never touch the network or files outside the workspace by
  construction, but for hostile, arbitrary code the deployment should run
  the whole service inside a container/VM.
* Windows hosts: no resource (memory/CPU) limits are enforced — only the
  timeout and output caps.
* Proof plans exist only for SQL injection, command injection and SSRF;
  anything else returns `not_verified`.
* The SQLi proof demonstrates the construction property on a fixture, not on
  the repository's own database layer.
